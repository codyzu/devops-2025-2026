## Connect the application to PostgreSQL

PostgreSQL is **required in this lab**, even if you chose another extension in Lab 42. Allow 45–75 minutes for this guided setup. If your database extension already works, keep it and demonstrate the same insertion and persistence checks below; do not replace its credentials, initialization, or PVC. Adapt the verification commands to your existing resource names.

### Prepare the namespace and files

Run these commands inside the course Ubuntu VM, from your own fork. Keep the app manifests in their existing directory:

```bash
cd "$(git rev-parse --show-toplevel)"
kubectl config set-context --current --namespace=quote-lab
mkdir -p labs/52-architecture
cp labs/20-containerized-node-app/db/init.sql labs/52-architecture/init.sql
cd labs/52-architecture
kubectl get storageclass
```

The manifest below uses k3s's `local-path` StorageClass. If it is missing, ask for help before continuing. This is storage on the course VM, not replicated storage or a backup.

Create a ConfigMap containing the existing initialization SQL:

```bash
kubectl create configmap quote-db-init --from-file=init.sql \
  --dry-run=client -o yaml > db-init-configmap.yaml
kubectl apply -f db-init-configmap.yaml
```

The SQL creates the `quotes` table and example data. Initialization runs only when PostgreSQL starts with an empty data directory; changing this ConfigMap does not migrate an existing database. Do not delete a PVC to apply a schema change.

### Create database configuration

For a new database, create a lab-only password and a Secret. Check for an existing Secret first:

```bash
kubectl get secret quote-db-secret
```

If it exists, reuse its configuration. If the result is `NotFound` and you are creating a **new** database, run:

```bash
db_password=$(openssl rand -hex 16)
kubectl create secret generic quote-db-secret \
  --from-literal=POSTGRES_USER=quote \
  --from-literal=POSTGRES_PASSWORD="$db_password" \
  --from-literal=POSTGRES_DB=quotes \
  --from-literal=DATABASE_URL="postgres://quote:$db_password@quote-db:5432/quotes"
unset db_password
```

Keep credentials out of Git and screenshots. Commit manifests that reference the Secret, not an export of its contents. The generated hex password is safe to include in this connection URL. Do not regenerate credentials for an existing PVC: PostgreSQL's initialization environment variables do not change an existing database user's password.

### Deploy storage, PostgreSQL, and its Service

Create `database.yaml`:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: quote-db-data
spec:
  accessModes:
    - ReadWriteOnce
  storageClassName: local-path
  resources:
    requests:
      storage: 1Gi
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: quote-db
spec:
  replicas: 1
  strategy:
    type: Recreate
  selector:
    matchLabels:
      app: quote-db
  template:
    metadata:
      labels:
        app: quote-db
    spec:
      containers:
        - name: postgres
          image: postgres:18
          envFrom:
            - secretRef:
                name: quote-db-secret
          ports:
            - containerPort: 5432
          readinessProbe:
            exec:
              command:
                - sh
                - -c
                - pg_isready -h 127.0.0.1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"
            initialDelaySeconds: 5
            periodSeconds: 5
          volumeMounts:
            - name: data
              mountPath: /var/lib/postgresql
            - name: init
              mountPath: /docker-entrypoint-initdb.d
              readOnly: true
      volumes:
        - name: data
          persistentVolumeClaim:
            claimName: quote-db-data
        - name: init
          configMap:
            name: quote-db-init
---
apiVersion: v1
kind: Service
metadata:
  name: quote-db
spec:
  selector:
    app: quote-db
  ports:
    - port: 5432
      targetPort: 5432
  type: ClusterIP
```

The [official PostgreSQL image documentation](https://hub.docker.com/_/postgres) describes its initialization and storage behavior. PostgreSQL 18 uses the parent mount `/var/lib/postgresql`; do not copy an older image's mount path without checking its documentation. `Recreate` avoids overlapping database Pods during a Deployment update. This single-instance teaching deployment has downtime during replacement and is not a production database HA design.

Apply and inspect:

```bash
kubectl apply -f database.yaml
kubectl rollout status deployment/quote-db --timeout=180s
kubectl get pvc quote-db-data
kubectl get pods -l app=quote-db
kubectl logs deployment/quote-db
```

Expect a Bound PVC and one Ready database Pod. If the rollout fails, inspect Pod events and the PVC before continuing. `pg_isready` checks whether PostgreSQL accepts connections; it does not prove that the app credentials or table queries work.

### Configure the application connection

Edit `../42-kubernetes/deployment.yaml`. Add this `env` entry under the existing `quote-app` container, alongside `image`, `ports`, and `readinessProbe`:

```yaml
env:
  - name: DATABASE_URL
    valueFrom:
      secretKeyRef:
        name: quote-db-secret
        key: DATABASE_URL
```

Merge it into an existing `env` list if you already have one. Keep three replicas and the `/health` readiness probe. The app consumes `DATABASE_URL`; setting only `POSTGRES_USER` and `POSTGRES_PASSWORD` in the app container does not configure its connection.

```bash
kubectl apply -f ../42-kubernetes/deployment.yaml
kubectl rollout status deployment/quote-app --timeout=120s
```

### Verify quote operations and persistence

In another VM terminal, start or restart the app port-forward:

```bash
kubectl port-forward svc/quote-app 8080:80
```

From your working VM terminal, insert a uniquely named quote through the application and read it back:

```bash
quote_marker="res509-$(date +%s)"
curl --fail --show-error --max-time 10 \
  --data-urlencode "author=RES509" \
  --data-urlencode "text=$quote_marker" \
  http://127.0.0.1:8080/quotes
curl --fail --show-error --max-time 10 http://127.0.0.1:8080/ -o /tmp/res509-quotes.html
grep -F "$quote_marker" /tmp/res509-quotes.html
```

Expect the marker in the returned page. If not, check that your Session 2 SELECT and INSERT handlers are implemented, inspect app logs, and verify the connection and table initialization. A passing `/health` is insufficient.

Replace the database Pod while keeping its PVC:

```bash
kubectl get pods -l app=quote-db
kubectl rollout restart deployment/quote-db
kubectl rollout status deployment/quote-db --timeout=180s
kubectl get pods -l app=quote-db
curl --fail --show-error --max-time 10 http://127.0.0.1:8080/ -o /tmp/res509-quotes-after.html
grep -F "$quote_marker" /tmp/res509-quotes-after.html
```

Expect a new database Pod and the same quote. Keep the marker value in this terminal until the check is complete. Save the two Pod names and the before/after quote result. Do not delete the PVC. Explain why this proves persistence across Pod replacement but not recovery after VM or disk loss.

## Add readiness and liveness probes

Enhance your deployment with health checks.

Example:

```yaml
livenessProbe:
  httpGet:
    path: /health
    port: 3000
  initialDelaySeconds: 5
  periodSeconds: 10

readinessProbe:
  httpGet:
    path: /health
    port: 3000
  initialDelaySeconds: 5
  periodSeconds: 5
```

Keep probes from your Lab 42 extension if they already meet this configuration. `/health` is deliberately independent of PostgreSQL; a database outage should not trigger an app restart loop. Verify database-backed operations separately.

Change only the liveness path to `/does-not-exist`, observe restart counts and events, then restore `/health`. Reuse existing evidence if you already demonstrated this in Lab 42.

Answer:

- What is the difference between readiness and liveness?
- Why does this matter in production?

## Build and publish a versioned image \{.no-step\}

You need two image versions to demonstrate a rollout.

If you already have a workflow from the previous course, you can reuse it.

Otherwise, keep it simple and build locally. First return to the application directory:

```bash
cd "$(git rev-parse --show-toplevel)/labs/20-containerized-node-app"
```

- Build a versioned image tag:
```bash
docker build -t quote-app:v1 -f docker/Dockerfile .
```

- Make your code change, then build a second version:
```bash
docker build -t quote-app:v2 -f docker/Dockerfile .
```

Build from `labs/20-containerized-node-app` in the VM. With the course k3s/containerd setup, import both tags before deploying or rolling back; Docker images are not automatically available to k3s.

Example (local, no registry):
```bash
docker save quote-app:v1 quote-app:v2 -o /tmp/quote-app-versions.tar
sudo k3s ctr images import /tmp/quote-app-versions.tar
```

## Roll back safely

Undo the broken rollout:

```bash
kubectl rollout undo deployment quote-app
kubectl rollout status deployment/quote-app --timeout=120s
```

Restore the saved manifest to the recovered image and probe configuration, then apply it and verify again. Rollback changes the cluster, not your Git files.

Verify:
- The application becomes healthy again
- The Deployment stabilizes
- Pods return to a ready state

Add a short note in `architecture-notes.md`:
- What did rollback change?
- What did rollback not change?
