<section class="title-center-body-left">
## <Icon name="i-tabler-database" />PVC: PersistentVolumeClaim

- A PVC requests persistent storage for a workload
- **Bound** means it is linked to a PersistentVolume (PV)
- The database Pod mounts that volume using its claim
- Replace the Pod, reuse the claim: data can survive
- Our local-path volume lives on the VM’s disk; it is not a backup
</section>

<section class="title-center-body-left">
## <Icon name="i-tabler-stack-2" />Which boundary failed?

- App and database containers share the Ubuntu VM's kernel
- Kubernetes replaces Pods inside that VM
- The PVC keeps database data across Pod replacement
- Our local-path storage still depends on the VM's disk
- Three app replicas on one VM do not survive losing that VM

Pod recovery, persistent storage, and backups solve different problems.
</section>

<section>
## <Icon name="i-tabler-arrows-exchange" />Rolling updates

Discuss an app Deployment using **RollingUpdate**:

- A changed Pod template starts a new rollout
- New Pods must become Ready before taking traffic
- Surge/unavailable settings control replacement
- Bad readiness can stall progress; inspect before proceeding

Build/import new images into k3s before rollout; Docker’s image store is separate.
</section>

<section>
## <Icon name="i-tabler-list-details" />Observe a Rollout

```bash
kubectl rollout status deployment quote-app
kubectl rollout history deployment quote-app
```

Read these as diagnostic examples in the app namespace.

- Status: has the Deployment progressed?
- History: which template revisions are retained?
- A stalled rollout needs diagnosis; it is not automatic rollback.
</section>

<section>
## <Icon name="i-tabler-rotate-2" />Rollback

Example: return to a retained previous Pod template:

```bash
kubectl rollout undo deployment quote-app
```

Verify readiness and app behavior after recovery.

Deployment rollback does not restore database data or undo schema changes. Keep saved manifests consistent with the intended version.
</section>
