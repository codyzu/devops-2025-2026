<section>
## <Icon name="i-tabler-stack-2" />Docker Compose is great

<p class="block-title">Compose manages services on one Docker host:</p>

- Define services together in YAML
- Restart containers using restart policies
- Scale compatible services with `up --scale`
- Keep a simple local development environment
</section>

<section>
## <Icon name="i-tabler-alert-triangle" />Compose limits

<p class="block-title">Compose does not give you:</p>

- Scheduling across machines
- Rescheduling workloads onto another host
- A consistent model for rolling updates
- A control plane that watches and reconciles state
</section>

<section class="">
## <Icon name="i-tabler-paw" />Pets vs Cattle

<div class="two-col">
<div>
<p class="block-title">Pets</p>
- Unique
- Named
- Manually cared for
</div>
<div>
<p class="block-title">Cattle</p>
- Replaceable
- Disposable
- Recreated automatically
</div>
</div>

Kubernetes treats Pods like cattle.
Persistent data needs storage that survives Pod replacement.
</section>

<section class="title-center-body-left">
## <Icon name="i-tabler-bulb" class="translate-y-[-0.1em]" />So what is Kubernetes?

<p class="block-title">Kubernetes is a system that:</p>

- Keeps your apps running
- Tries to match **desired state** to **actual state**
- Continuously reconciles the difference

You describe *what you want*.
Kubernetes does the repetitive work.
</section>

<section>
## <Icon name="i-tabler-refresh" />The control loop idea

<div class="two-col">
<div>
<p class="block-title">Desired state:</p>
- “I want 3 copies of this app running”
</div>
<div>
<p class="block-title">Actual state:</p>
- “Only 2 are running right now”
</div>
</div>
<p class="block-title">Controller loop:</p>
- “Start 1 more”

<p class="block-title">This loop never stops.</p>
</section>

<section>
## <Icon name="i-tabler-cube" />Core objects we will use

<p class="block-title">Keep it simple:</p>

- **Pod**: the smallest unit that runs
- **Deployment**: manages replicas and updates
- **Service**: stable networking to reach the app

We will ignore the rest for now.
</section>

<section>
## <Icon name="i-tabler-package" />Pod: the unit of execution

<p class="block-title">A Pod is:</p>

- One or more containers that run together
- Shared networking inside the Pod
- Usually short-lived, replaceable

<p class="block-title">Key idea:</p>
- You do not manage Pods manually in production
</section>

<section>
## <Icon name="i-tabler-repeat" />Deployment: desired state for Pods

<p class="block-title">A Deployment lets you say:</p>

- Which image to run
- How many replicas you want
- How updates should roll out

It creates and replaces Pods for you.
</section>

<section>
## <Icon name="i-tabler-hierarchy" />Controller hierarchy

<div class="two-col">
<Mermaid class="mt-5" chart={String.raw`
flowchart TD
  A(Deployment) --> B(ReplicaSet)
  B --> C(Pod)
`} />

<div>
- You interact with the Deployment.
- The Deployment manages ReplicaSets.
- The ReplicaSet ensures the right number of Pods exist.
</div>
</div>

If a Pod disappears, the ReplicaSet creates a new one.
</section>

<section>
## <Icon name="i-tabler-network" />Service: stable access

Pods come and go.
IPs change.
A Service gives you:

- A stable name
- A stable virtual IP
- Routing to eligible, Ready Pods

Today we will use a simple local Service.
</section>

<section>
## <Icon name="i-tabler-file-code" />Everything is “configuration as code”

Kubernetes is declarative.

You apply YAML, for example:

- deployment.yaml
- service.yaml

You can version it in git, review it, and automate it in CI.
</section>

<section class="title-center-body-left">
## <Icon name="i-tabler-arrows-exchange" />Commands and manifests

- **Imperative:** request a change with a command
- **Declarative:** apply desired state from saved YAML
- A Deployment reconciles replicas with either approach
- A bare Pod has no ReplicaSet to replace it after deletion

Keep the desired state in Git; use `apply` to reproduce it.
</section>

<section class="title-center-body-left">
## <Icon name="i-tabler-network" />Our cluster today

- `kubectl` sends requests to the API server
- The control plane schedules and reconciles work
- A node runs Pods through its container runtime
- k3s runs both roles on our single Ubuntu VM
- A namespace groups resources inside the cluster

Three replicas on one VM do **not** survive losing that VM.
</section>

<section class="title-center-body-left">
## <Icon name="i-tabler-file-code" />Read the manifest

- Deployment: desired replica count and Pod template
- Pod label: `app: quote-app`
- Service selector: the same `app: quote-app`
- Service port `80` forwards to app port `3000`

Find those fields in Lab 42 before applying the YAML.
</section>

<section class="title-center-body-left">
## <Icon name="i-tabler-heart" />Ready versus alive

- **Readiness:** should normal Service traffic reach this Pod?
- **Liveness:** should this container be restarted?
- Readiness failure alone does not restart a container
- Our `/health` checks HTTP, not database operations

A healthy probe proves only what its endpoint checks.
</section>

<section>
## <Icon name="i-tabler-terminal-2" />Your debugging toolkit

You will mostly use:

- `kubectl get ...`
- `kubectl describe ...`
- `kubectl logs ...`
- `kubectl apply -f ...`
- `kubectl delete ...`
- `kubectl rollout status ...`

Use status → events → logs to explain a failure.
</section>

<section>
## <Icon name="i-tabler-eye" />How to observe what is happening

<p class="block-title">When something is wrong, check in this order:</p>

- Status: `kubectl get`
- Details and events: `kubectl describe`
- Application output: `kubectl logs`

This is your debugging loop, just as `docker compose ps` and `logs` were in RES507.
</section>

## <Icon name="i-tabler-bug" class="translate-y-[-0.1em]" />Intentional failure

<p class="block-title">You will intentionally create a failure:</p>

- Change the readiness path to `/does-not-exist`
- Observe a new Pod running but **not Ready**
- Find the probe's HTTP 404 in its events

Restore `/health`, re-apply, and verify recovery.

Old healthy replicas may remain available during the failed rollout.
</section>
