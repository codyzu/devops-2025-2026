
## Create a Deployment

The baseline deploys the application **without PostgreSQL**. Its `/health` route returns `{"ok": true}` without querying the database. Your completed quote page and quote insertion may fail until you add database integration; that does not invalidate this health-only baseline.

Create a file named `deployment.yaml` with the following content:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: quote-app
spec:
  replicas: 1
  selector:
    matchLabels:
      app: quote-app
  template:
    metadata:
      labels:
        app: quote-app
    spec:
      containers:
        - name: quote-app
          image: quote-app:local
          imagePullPolicy: IfNotPresent
          ports:
            - containerPort: 3000
          readinessProbe:
            httpGet:
              path: /health
              port: 3000
            initialDelaySeconds: 3
            periodSeconds: 5
```

Before applying, identify `replicas`, the Pod template’s `app: quote-app` label, and the Deployment selector matching that label. A Deployment manages ReplicaSets, which maintain the requested Pods.

**Readiness** determines eligibility for normal Service traffic. **Liveness** can trigger container restart. This baseline uses readiness only. Neither probe validates database behavior unless its endpoint actually checks the database.

Apply it:

```bash
kubectl apply -f deployment.yaml
kubectl rollout status deployment/quote-app --timeout=120s
```

Observe:

```bash
kubectl get pods
kubectl describe pod POD_NAME
```

Continue when the rollout completes and your application Pod shows `1/1` in the `READY` column. `Running` alone is not enough.

## Expose the application with a Service

Create `service.yaml`:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: quote-app
spec:
  selector:
    app: quote-app
  ports:
    - port: 80
      targetPort: 3000
  type: ClusterIP
```

Identify the Service selector matching the Pod label. `port: 80` is the Service port; `targetPort: 3000` is the application’s listening port. A `containerPort` declaration alone does not make the application listen there.

Apply it:

```bash
kubectl apply -f service.yaml
```

Verify:

```bash
kubectl get svc
```

## Access the health endpoint

In a VM terminal, start port-forwarding and leave it running:

```bash
kubectl port-forward svc/quote-app 8080:80
```

Wait for the `Forwarding from 127.0.0.1:8080` message. In a **second terminal inside the same VM**, check the endpoint:

```bash
curl --fail --show-error --max-time 5 http://127.0.0.1:8080/health
```

Expect JSON containing `"ok": true`. You are checking application health; quote retrieval and insertion are part of the database extension.

`ClusterIP` is internal to the cluster. This port-forward listens on the **VM's loopback interface**, not your laptop's. To use your laptop browser, keep the VM port-forward running and open another terminal **on your laptop**, using Bash or zsh (on Windows, use WSL Bash):

```bash
printf "VM SSH username: "
read -r vm_user
printf "VM IP address: "
read -r vm_host
ssh -N -L 8080:127.0.0.1:8080 "$vm_user@$vm_host"
```

Use the same SSH destination and connection options you normally use to reach the course VM. Leave this tunnel running, then open [the health endpoint](http://localhost:8080/health) in your laptop browser. If using VS Code Remote SSH, you can instead forward the VM's port 8080 through its Ports panel.

A port-forward to a Service selects **one Pod** and forwards directly to it. It does not demonstrate Service load balancing or readiness-based traffic selection. If that Pod disappears, restart the VM port-forward; other Ready replicas do not keep that particular forwarding session alive.

## Introduce a controlled readiness failure

This step is required for grading. Predict first: will the container restart, and can old healthy replicas still serve requests?

In `deployment.yaml`, change only the readiness probe's path from `/health` to `/does-not-exist`. Keep the image, application port, and three replicas unchanged. Apply the change:

```bash
kubectl apply -f deployment.yaml
kubectl rollout status deployment/quote-app --timeout=60s
kubectl get pods -l app=quote-app
kubectl get rs -l app=quote-app
```

The rollout command is expected to time out because the new Pods cannot become Ready. The timeout stops your wait; Kubernetes continues trying to reconcile the Deployment.

Find a new Pod showing `0/1` in the `READY` column. Replace `POD_NAME` with that Pod's name and inspect it:

```bash
kubectl describe pod POD_NAME
kubectl logs POD_NAME
kubectl get events --sort-by=.metadata.creationTimestamp
```

Look for an `Unhealthy` event reporting a readiness probe failure with HTTP status 404. The container can be `Running` while its Pod is not Ready. A failing readiness probe does not itself restart the container.

Inspect the Service's endpoint readiness:

```bash
kubectl get endpointslices -l kubernetes.io/service-name=quote-app -o yaml
```

In each endpoint, compare `targetRef.name` with your Pod list and find `conditions.ready`. Expect `false` for the new failing Pod and `true` for healthy Pods.

The new unready Pods are not eligible for normal Service traffic. With the default rolling-update strategy, old healthy replicas can remain available while the rollout is stalled. The Service may therefore still work; a total outage is **not** the expected proof of this failure. Do not use a successful port-forward request as proof that the new Pods are Ready.

An invalid image tag would produce a different failure (`ErrImagePull` or `ImagePullBackOff`), rather than a readiness probe failure. Use the bad probe path for this exercise so you can distinguish the two.

Restore the probe path to `/health` in the file, then verify recovery:

```bash
kubectl apply -f deployment.yaml
kubectl rollout status deployment/quote-app --timeout=120s
kubectl get pods -l app=quote-app
```

Confirm the rollout completes and three Pods are Ready once the rollout settles. Restart port-forwarding if needed, and repeat the `/health` request.
