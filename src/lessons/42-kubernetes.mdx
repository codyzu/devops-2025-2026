### Set up k3s and kubectl access \{.no-step\}

<details>
  <summary><strong>Click to expand: k3s + kubectl setup on Ubuntu Server</strong></summary>

  Check whether k3s is already installed:

  ```bash
  command -v k3s
  ```

  If this prints a path, **skip installation** and continue with kubeconfig setup below. Reuse your existing cluster; do not reinstall or change its runtime during this lab.

  If it prints nothing, install a single-node cluster with the default containerd runtime:

  ```bash
  sudo apt update
  curl -sfL https://get.k3s.io -o /tmp/install-k3s.sh
  sudo sh /tmp/install-k3s.sh
  ```

  The installer needs administrator privileges to create the system service. Docker remains your image build tool; k3s runs the Kubernetes workloads.

  Check the service:

  ```bash
  sudo systemctl status k3s --no-pager
  ```

  If it is inactive or failed, inspect its logs and ask for help before continuing. Do not rerun the installer as a troubleshooting step.

  ```bash
  sudo journalctl -u k3s -n 50 --no-pager
  ```

  Copy the cluster configuration into your own home directory. Run these commands as your normal VM user:

  ```bash
  mkdir -p "$HOME/.kube"
  sudo install -m 600 -o "$(id -u)" -g "$(id -g)" \
    /etc/rancher/k3s/k3s.yaml "$HOME/.kube/config"
  export KUBECONFIG="$HOME/.kube/config"

  # Persist once for future Bash sessions
  if ! grep -qxF 'export KUBECONFIG="$HOME/.kube/config"' "$HOME/.bashrc"; then
    echo 'export KUBECONFIG="$HOME/.kube/config"' >> "$HOME/.bashrc"
  fi
  ```

  This replaces the VM user's default kubeconfig with this course cluster's configuration. If you already use that file for another cluster, preserve it and ask for help first. Do not commit kubeconfig to Git.

  Use ordinary `kubectl`, **not `sudo kubectl`**. Setting `KUBECONFIG` explicitly ensures it uses your writable home-directory copy rather than the protected system file.

  Wait for the node to become Ready, then verify access:

  ```bash
  kubectl wait --for=condition=Ready node --all --timeout=120s
  kubectl get nodes -o wide
  kubectl get pods -A
  ```

  Continue only when your node is `Ready`. If the wait times out, inspect the service logs above and ask for help.

## Build and import your image for Kubernetes

In your Ubuntu VM terminal, return to the root of your own lab repository, then enter the existing application directory:

```bash
cd "$(git rev-parse --show-toplevel)"
git status
git branch --show-current
cd labs/20-containerized-node-app
ls app/package.json app/package-lock.json docker/Dockerfile
```

Build the image using the lab directory as its context:

```bash
docker build -t quote-app:local -f docker/Dockerfile .
```

**Import the image before deploying it.** Default k3s uses containerd, whose image store is separate from Docker's. A successful Docker build alone does not make the image available to Kubernetes.

```bash
docker save quote-app:local -o /tmp/quote-app.tar
sudo k3s ctr images import /tmp/quote-app.tar
sudo k3s ctr images list | grep 'quote-app:local'
```

Continue only when the image list contains `docker.io/library/quote-app:local`. All three operations must happen on the same Ubuntu VM that runs your single-node cluster.

If you change application code later, build and import a new tag, such as `quote-app:v2`, then update the Deployment's image to that tag. Applying unchanged YAML does not deploy a rebuilt image automatically.

<details>
  <summary><strong>Troubleshooting: image not found or cluster setup</strong></summary>

  For `ImagePullBackOff` or `ErrImagePull`, inspect the Pod's events with `kubectl describe pod <pod-name>`. Confirm that the Deployment image matches the imported tag exactly and that the import happened on this VM.

  After correcting an import for the existing tag, delete the failing Pod to let its Deployment create a replacement:

  ```bash
  kubectl delete pod <pod-name>
  kubectl get pods -w
  ```

  Press Ctrl+C to stop watching.

  If you are unsure whether the problem is your application image, try a public image:

  ```bash
  kubectl create deployment nginx-test --image=nginx
  kubectl rollout status deployment/nginx-test --timeout=120s
  ```

  If nginx becomes available, the cluster can run that public workload; investigate your application image and configuration. If it fails, inspect its events too: registry/network access may be the cause.

  Remove the diagnostic Deployment when finished:

  ```bash
  kubectl delete deployment nginx-test
  ```
</details>

## Create a Deployment

The baseline deploys the application **without PostgreSQL**. Its `/health` route returns `{"ok": true}` without querying the database. Your completed quote page and quote insertion may fail until you add database integration; that does not invalidate this health-only baseline.

Create a file named `deployment.yaml` with the following content:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: quote-app
spec:
  replicas: 1
  selector:
    matchLabels:
      app: quote-app
  template:
    metadata:
      labels:
        app: quote-app
    spec:
      containers:
        - name: quote-app
          image: quote-app:local
          imagePullPolicy: IfNotPresent
          ports:
            - containerPort: 3000
          readinessProbe:
            httpGet:
              path: /health
              port: 3000
            initialDelaySeconds: 3
            periodSeconds: 5
```

Apply it:

```bash
kubectl apply -f deployment.yaml
```

Observe:

```bash
kubectl get pods
kubectl describe pod <pod-name>
```

## Expose the application with a Service

Create `service.yaml`:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: quote-app
spec:
  selector:
    app: quote-app
  ports:
    - port: 80
      targetPort: 3000
  type: ClusterIP
```

Apply it:

```bash
kubectl apply -f service.yaml
```

Verify:

```bash
kubectl get svc
```

## Access the health endpoint

In a VM terminal, start port-forwarding and leave it running:

```bash
kubectl port-forward svc/quote-app 8080:80
```

Wait for the `Forwarding from 127.0.0.1:8080` message. In a **second terminal inside the same VM**, check the endpoint:

```bash
curl --fail --show-error --max-time 5 http://127.0.0.1:8080/health
```

Expect JSON containing `"ok": true`. You are checking application health; quote retrieval and insertion are part of the database extension.

`ClusterIP` is internal to the cluster. This port-forward listens on the **VM's loopback interface**, not your laptop's. To use your laptop browser, keep the VM port-forward running and open another terminal **on your laptop**:

```bash
read -r -p "VM SSH username: " vm_user
read -r -p "VM IP address: " vm_host
ssh -N -L 8080:127.0.0.1:8080 "$vm_user@$vm_host"
```

Use the same SSH destination and connection options you normally use to reach the course VM. Leave this tunnel running, then open [the health endpoint](http://localhost:8080/health) in your laptop browser. If using VS Code Remote SSH, you can instead forward the VM's port 8080 through its Ports panel.

A port-forward to a Service selects **one Pod** and forwards directly to it. It does not demonstrate Service load balancing or readiness-based traffic selection. If that Pod disappears, restart the VM port-forward; other Ready replicas do not keep that particular forwarding session alive.

## Scale the Deployment

In `deployment.yaml`, change `replicas: 1` to `replicas: 3`. Apply the file so the saved desired state matches the cluster:

```bash
kubectl apply -f deployment.yaml
kubectl rollout status deployment/quote-app --timeout=120s
kubectl get pods -l app=quote-app -o wide
```

Confirm that three Pods have `READY` equal to `1/1`.

Discuss:

- What does scaling change?
- Does scaling the application also create a database or validate quote operations?

Keep `replicas: 3` in the file for the following exercises. Reapplying a file with `replicas: 1` would undo the scaling change.

## Observe Pod replacement

In one VM terminal, watch the Pods:

```bash
kubectl get pods -l app=quote-app -w
```

In another VM terminal, list the Pods and delete one. Replace `POD_NAME` below with a name from the list:

```bash
kubectl get pods -l app=quote-app
kubectl delete pod POD_NAME
```

Observe a replacement Pod appearing with a new name and becoming Ready. The Deployment's ReplicaSet reconciles the replica count back to three. Press Ctrl+C to stop watching once the replacement is Ready.

The remaining Ready Pods can remain eligible for Service traffic while the replacement starts. This exercise demonstrates reconciliation, not a guarantee of zero downtime. If the deleted Pod was selected by your port-forward, restart that command and repeat the health request.

## Introduce a controlled readiness failure

This step is required for grading.

In `deployment.yaml`, change only the readiness probe's path from `/health` to `/does-not-exist`. Keep the image, application port, and three replicas unchanged. Apply the change:

```bash
kubectl apply -f deployment.yaml
kubectl rollout status deployment/quote-app --timeout=60s
kubectl get pods -l app=quote-app
kubectl get rs -l app=quote-app
```

The rollout command is expected to time out because the new Pods cannot become Ready. The timeout stops your wait; Kubernetes continues trying to reconcile the Deployment.

Find a new Pod showing `0/1` in the `READY` column. Replace `POD_NAME` with that Pod's name and inspect it:

```bash
kubectl describe pod POD_NAME
kubectl logs POD_NAME
kubectl get events --sort-by=.metadata.creationTimestamp
```

Look for an `Unhealthy` event reporting a readiness probe failure with HTTP status 404. The container can be `Running` while its Pod is not Ready. A failing readiness probe does not itself restart the container.

Inspect the Service's endpoint readiness:

```bash
kubectl get endpointslices -l kubernetes.io/service-name=quote-app -o yaml
```

The new unready Pods are not eligible for normal Service traffic. With the default rolling-update strategy, old healthy replicas can remain available while the rollout is stalled. The Service may therefore still work; a total outage is **not** the expected proof of this failure. Do not use a successful port-forward request as proof that the new Pods are Ready.

An invalid image tag would produce a different failure (`ErrImagePull` or `ImagePullBackOff`), rather than a readiness probe failure. Use the bad probe path for this exercise so you can distinguish the two.

Restore the probe path to `/health` in the file, then verify recovery:

```bash
kubectl apply -f deployment.yaml
kubectl rollout status deployment/quote-app --timeout=120s
kubectl get pods -l app=quote-app
```

Confirm the rollout completes and three Pods are Ready once the rollout settles. Restart port-forwarding if needed, and repeat the `/health` request.
