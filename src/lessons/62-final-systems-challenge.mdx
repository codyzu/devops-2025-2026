## Scenario

A small startup deployed the Quote API using Kubernetes.

This fictional system is deliberately different from the corrected Lab 52 setup. It has the following characteristics:

<Mermaid class="" chart={String.raw`
flowchart TD
  U[Users] --> I[Ingress or NodePort]
  I --> P[Single Pod: quote-api + postgres in same container]
  P --> E[Credentials committed in manifest]
  P --> N[Single node dependency]
  P --> R[No probes, no limits]
`} />

- A single Pod runs the application
- The PostgreSQL database runs inside the same container, storing data in its writable container layer
- There are no readiness or liveness probes
- There are no resource limits
- The app uses a Recreate update strategy: old Pods are stopped before replacements become available
- Database credentials are literal environment values committed in the manifest
- The node and its disk are single points of failure; there is no tested backup/restore procedure

The team believes the system is production ready.

Your task is to evaluate this architecture and redesign it so it could realistically run in production.

## Design an improved architecture

Create a new section in `final-architecture.md`:

```text
Production Architecture
```

Design a production-ready version of the system.

Your design should include:

- An application Deployment
- A Service exposing the application
- A PostgreSQL database with persistent storage
- Multiple application replicas
- A safe app rollout strategy
- Secret references with a way to provision credentials without committing them
- Explicit VM/node and storage failure boundaries, including backup and restore

Explain what happens if a Pod fails and if the VM or disk is lost. Distinguish availability from data recovery: a PVC alone is not a backup, and multiple replicas on one node do not remove that node dependency.

Reuse and annotate your Lab 52 diagram, or create a new **architecture diagram** that shows:

- users
- Kubernetes services
- application pods
- database
- storage
- nodes or infrastructure layer

Consider using:

- draw.io
- Excalidraw
- diagrams.net
- hand-drawn diagram exported as PNG

Embed or link the diagram in `final-architecture.md`. Mark the proposed changes clearly; you do not need to redraw verified parts of Lab 52.

## Explain your operational strategy


Add a section titled:

```text
Operational Strategy
```

Keep a few operational bullets covering the prompts below; explain details during your presentation.

### How does the system scale?

Explain how your design handles increased traffic and load.

### How are updates deployed safely?

Describe the app rollout strategy and how you would verify or roll back a bad version. Explain why Deployment rollback does not restore database contents or reverse a schema migration.

### How are failures detected?

Explain what mechanisms detect unhealthy pods or services.

### Which Kubernetes controllers handle recovery?

Identify which controllers recreate or stabilize components when failures occur. Explain what still needs a backup/restore process or infrastructure recovery beyond those controllers.
