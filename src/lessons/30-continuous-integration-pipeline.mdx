In this lab, you will extend the work from the previous sessions and build a **real Continuous Integration pipeline** for your application.

Unlike the CI preview you may have done earlier, this lab focuses on **trust**: checking that your application installs, builds, starts, and answers a health request every time you push code. You will also identify what these checks leave untested.

## Introduce the CI workflow

You will use **GitHub Actions** to define your pipeline as code.

Create the workflow directory if it does not already exist:

```bash
mkdir -p .github/workflows
```

Create or edit `.github/workflows/ci.yml`, reusing the filename from lesson 16. If you previously named it `ci.yaml`, rename that file to `ci.yml` rather than creating a duplicate.

The workflow must be in `.github/workflows` at the **repository root**, not inside the lab directory. GitHub Actions starts from its own checkout; your local terminal directory does not set the runner's directory.

## Define pipeline triggers

Configure the workflow so it runs on both pushes and pull requests.

Start with the following content:

```yaml
name: CI

on:
  push:
  pull_request:
```

This ensures validation runs whenever code is proposed or updated.

## Define the build job

Define a job that runs on a Linux runner:

```yaml
jobs:
  build:
    runs-on: ubuntu-latest
```

All validation steps will live inside this job. Indent `steps:` under `build`, at the same level as `runs-on`. Each step belongs inside that list.

Use the complete workflow below to check the nesting after assembling the pieces.

## Check out the repository

Add a step to fetch your repository contents:

```yaml
    steps:
      - name: Check out repository
        uses: actions/checkout@v7
```

This is equivalent to cloning the repository locally.

## Run fast checks

Before building containers, install dependencies reproducibly and check JavaScript syntax.

Append these steps to the job's `steps` list:

```yaml
      - name: Set up Node.js
        uses: actions/setup-node@v7
        with:
          node-version: "24"

      - name: Install dependencies
        working-directory: labs/20-containerized-node-app/app
        run: npm ci

      - name: Check JavaScript syntax
        working-directory: labs/20-containerized-node-app/app
        run: |
          node --check app.js
          node --check server.js
```

`npm ci` installs the versions recorded in the committed `package-lock.json` and fails if its dependency declarations disagree with `package.json`.

`node --check` catches syntax errors. It does **not** execute the application, resolve its imports, or verify its behavior.

The scaffold's `test` script is a placeholder that prints "Error: no test specified" and exits with status 1. `npm test --if-present` would still run it because the script exists. Leave it out of the baseline pipeline; replace it with real tests if you choose the testing extension.

## Build the Docker image

Add a step to build the application image:

```yaml
      - name: Build Docker image
        working-directory: labs/20-containerized-node-app
        run: docker build -t quote-app -f docker/Dockerfile .
```

The working directory makes `.` the lab directory. This is the build context expected by the Dockerfile's `COPY app/` instructions. A successful build produces an image; it does not prove that the image starts.

## Run a container smoke test

A successful build is not enough. Start the built image and check that `/health` responds successfully with JSON containing `"ok": true`.

Append these steps:

```yaml
      - name: Run container smoke test
        run: |
          docker run -d --name quote-app -p 3000:3000 quote-app
          for attempt in $(seq 1 30); do
            if curl --fail --silent --show-error \
              --connect-timeout 1 --max-time 2 \
              http://localhost:3000/health -o /tmp/quote-app-health.json \
              && node -e 'const assert = require("node:assert/strict"); const fs = require("node:fs"); assert.equal(JSON.parse(fs.readFileSync("/tmp/quote-app-health.json", "utf8")).ok, true);'; then
              echo "Health check passed"
              exit 0
            fi
            sleep 1
          done
          echo "Health check failed"
          exit 1

      - name: Show container diagnostics
        if: failure()
        run: |
          docker ps -a
          docker inspect quote-app || true
          docker logs quote-app || true

      - name: Stop container
        if: always()
        run: docker rm -f quote-app || true
```

Each HTTP request has a timeout. The loop allows up to 30 attempts with a one-second pause between attempts; this is not an exact 30-second deadline. Add a five-minute job timeout in the complete workflow to bound the whole job.

Diagnostics run when a previous step fails, and cleanup runs even after failure.

The application listens on `0.0.0.0:3000`, and the Dockerfile starts it with `npm start`. This baseline runs the image without PostgreSQL. The `/health` route does not query the database, so it can pass while the quote page or quote insertion fails.

### Compare the complete workflow

Your repository-root `.github/workflows/ci.yml` should contain:

```yaml
name: CI

on:
  push:
  pull_request:

permissions:
  contents: read

jobs:
  build:
    runs-on: ubuntu-latest
    timeout-minutes: 5
    steps:
      - name: Check out repository
        uses: actions/checkout@v7

      - name: Set up Node.js
        uses: actions/setup-node@v7
        with:
          node-version: "24"

      - name: Install dependencies
        working-directory: labs/20-containerized-node-app/app
        run: npm ci

      - name: Check JavaScript syntax
        working-directory: labs/20-containerized-node-app/app
        run: |
          node --check app.js
          node --check server.js

      - name: Build Docker image
        working-directory: labs/20-containerized-node-app
        run: docker build -t quote-app -f docker/Dockerfile .

      - name: Run container smoke test
        run: |
          docker run -d --name quote-app -p 3000:3000 quote-app
          for attempt in $(seq 1 30); do
            if curl --fail --silent --show-error \
              --connect-timeout 1 --max-time 2 \
              http://localhost:3000/health -o /tmp/quote-app-health.json \
              && node -e 'const assert = require("node:assert/strict"); const fs = require("node:fs"); assert.equal(JSON.parse(fs.readFileSync("/tmp/quote-app-health.json", "utf8")).ok, true);'; then
              echo "Health check passed"
              exit 0
            fi
            sleep 1
          done
          echo "Health check failed"
          exit 1

      - name: Show container diagnostics
        if: failure()
        run: |
          docker ps -a
          docker inspect quote-app || true
          docker logs quote-app || true

      - name: Stop container
        if: always()
        run: docker rm -f quote-app || true
```

## Break the pipeline intentionally

This step is **required for grading**.

You must intentionally introduce a failure, observe a failing CI run on GitHub, then fix the issue and push a successful run.  
Keep the failed run URL. During the final review, show that run and identify the failing step and the log message that explains the cause.

Examples:

- Change the health check URL to a non-existent path
- Introduce a JavaScript syntax error and observe the syntax check fail
- Introduce a syntax error in the Dockerfile
- Break the application startup

Commit and push, then observe:

- The pipeline failing
- Clear error logs
- Automatic detection of broken changes

Fix the issue and push again. Keep the recovery run URL and the fixing commit SHA.

Record the failed step, the cause, and why your change fixes it in a short note in the repository. Do not remove or bypass the failing check to get green. Keep both runs available as grading evidence.

## Understand what CI gives you \{.no-step\}

A green baseline run means that, for the checked commit on this runner:

- Dependencies installed from the lockfile
- The two JavaScript files passed syntax checks
- The Docker image built
- The container answered `/health` with the expected JSON value

It does **not** prove that database connections, quote retrieval, insertion, persistence, security, performance, or production deployment work. Explain at least one failure that could still occur with green CI.

CI provides a signal. It becomes a merge gate only when branch protection or repository rules require its checks to pass. This lab does not configure those rules.
